# AI 创作可观测性（Observability · 跨切面运行时平面）

> **定位**：这是此前系统**唯一完全缺失**的一层——**可观测性**。架构 / 分层已稳定（用户评各维 10/10），但「系统到底跑得好不好」只能**凭感觉**。Observability 提供 **Workflow → 指标 → 仪表盘**，让系统优化**数据驱动**，而非拍脑袋。
>
> **不属于新 Layer**：它是**跨切面（cross-cutting）运行时平面**，依附于编排器与各层埋点，不进入 L1–L6 主栈。与 Context Engine / 能力编排器 / Delta Review / Build 同为「运行时增强」。

---

## 1. 采集点（Metrics Sources）

编排器在每轮 Loop、每层调用时**埋点**，写入指标流（可被 `tools/` 脚本读取，落 JSON/时序）：

- **Loop 级**：每章回归闭环轮数、门禁失败原因分布。
- **层级**：各 Plugin（planner/context/workflow/capability.*/review）调用耗时、版本（见 `AI编排器.md` §6）。
- **产物级**：Build 标识（见 `流程体系_小说创作.md` §3.1）含 NKB 版本 / Context Hash / 审查版本 / 引擎版本。

---

## 2. 核心指标（Dashboard）

| 指标 | 说明 | 用途 |
|------|------|------|
| 平均 Loop 次数 | 每章回归闭环轮数（目标趋近 1–2） | 评估门禁松紧 / 修复效率 |
| 致命命中率 | Fatal A/B 触发率（按章） | 评估写作对话 / 规范预防效果 |
| 读者指数趋势 | RI 随章变化曲线 | 监测体验衰减（早期预警） |
| CI 趋势 | 一致性指数随章 | 监测事实漂移 |
| 修复成功率 | 一次修复即 PASS 比例 | 评估修复三分（工程/编辑/读者）有效性 |
| Context 大小 | 每章 Final Context Token 数 | 监测上下文膨胀（见 `AI上下文引擎.md` §2.5） |
| 压缩比例 | 压缩前/后体积比 | 评估 Context Engine 效率 |
| 静态/动态评测耗时 | 分轨后耗时对比 | 验证 §7.10 静态/动态分轨提速 |
| 派生数据新鲜度 | Derived.md 距上次重算的章数 | 监测图谱是否滞后（见 `NKB.md` §2.3） |

## 3. 仪表盘形态（Dashboard）

```
章节 │ Loop次数 │ Fatal率 │ RI趋势 │ CI趋势 │ 修复率 │ Context │ 压缩比
001  │   3     │  12%   │  87↘  │ 98%↘  │  70%  │ 28k   │ 3.5:1
002  │   2     │   5%   │  88→  │ 99%→  │  85%  │ 26k   │ 3.8:1
...
```

- 仪表盘是**元闭环（第三层闭环，`审查体系.md` §7.8）**的输入：Loop 次数持续偏高 → 评估是否门禁过严；RI 趋势下滑 → 评估是否需调 Profile 权重；Context 膨胀 → 评估 Context Budget 是否要上调。
- **数据驱动优化**：上述任一指标的异常，都转化为对 宪法/规范/流程/脚本/Prompt 的具体反补（System Update 路径，`审查体系.md` §7.6.1），而非凭感觉改系统。

---

## 4. 与架构关系

```
编排器 Loop ──(埋点)──▶ 指标流 ──(聚合)──▶ 仪表盘 ──▶ 元闭环反补
        ↑________________ 跨切面，不新增 Layer ________________│
```

> Observability 让「AI 创作运行平台」从「能跑」升级为「能被度量、能被优化」——这是成熟工程系统的标志，也是用户指明下一步重点「完善运行时」的核心一环。
