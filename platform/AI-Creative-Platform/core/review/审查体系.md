# 审查体系（重构版 · v4.3 · 四大支柱 + 五阶段回归闭环）

> **定位**：《道士也玩火力覆盖》创作流程中「审查」环节的**全面重构方案（v4.2）**。基于 `审查参考.txt` 的 10 大模块框架，吸收 v2（权重/Fatal/元规则/RE/Risk/ID/重复4类/WBU）、v3（Fatal A/B / Profile 权重 / RE 五维 / Risk 概率 / CI / NH / 版本 / 文档拆分）、v4（读者审查升一级支柱·四大支柱）与 **v4.2（新增叙事/对白/冲突三编辑模块 → 13 模块；读者审查拆 `reader/` 子目录；NH 重拆五维 Story/Reader/Engineering/Narrative/Commercial；Persona 按类型加权；新增沉浸感 Immersion 与情绪曲线 Emotion Curve）**。
> **核心变化（v4）**：原「10 模块 + RE 子维度」重构为**四支柱各司其职**——专业编辑审查（质量）≠ AI 工程审查（错误）≠ 读者审查（体验），三者独立评分、互不替代，由发布门禁综合放行。例：编辑给世界观 98/逻辑 99/设定 100，读者仍可能因「不关心」而弃书。
> **与既有文档关系**：主文档=核心规则（原则/四支柱/流程），检查项在 `checks/`、权重在 `profiles/`、脚本在 `tools/`。既有 `流程体系_小说创作.md` 的 §3/附录A/§5 降级为旧版参考；双对话架构保留为前提。
> **v4.3 新增（流程升级）**：在四支柱之上引入**五阶段回归闭环**——写作→审查→修复→回归审查→定稿；章节状态机（Draft→…→Published）；门禁驱动的 Review Loop Engine；修复三分（工程/编辑/读者）；统一验收门（任何修改必须重跑三支柱门禁才进 Approved）；根因反补（Problem→RootCause→Rule→Workflow→Prompt→Script）；经验反馈层（+Memory）；三层闭环（章节/项目/体系元闭环），其中**第三层体系元闭环**补齐了此前唯一缺失的「流程自我演进」环节。
> **形成依据**：审查实践教训 ＋ `审查参考.txt` ＋ 用户 v2/v3/v4 升级意见。

## 0. 双重架构

本体系有两套正交的「层」，**不要混淆**：

### A. 维护四层（决定规则怎么存、怎么扩，v3 引入）
```
L1 元规则 Meta Rules  →  L2 模块/支柱  →  L3 检查项(checks/)  →  L4 脚本(tools/)
```
新增检查项 = 改 `checks/`；换类型 = 切 `profiles/`；新类才动 L2/L1。

### B. 审查四支柱（决定审查从哪几个视角打分，v4 引入）
```
审查体系
├─ 支柱1  专业编辑审查（质量）   → 综合分 ES（Profile 加权）
├─ 支柱2  AI工程审查（错误）     → CI 指数 / AI 错误密度
├─ 支柱3  读者审查（体验）       → Reader Index / PI / 角色模拟
└─ 支柱4  发布门禁（放行）       → 综合三支柱 + Fatal A/B
```
**三视角独立评分，互不替代**：编辑质量高 ≠ 读者爱看；工程无错 ≠ 体验佳。门禁综合三者。

## 1. 元规则 Meta Rules（L1 · 最高优先级）

1. **不冲突**：新增规则不与已有冲突。
2. **先抽象后特例**：同类问题优先抽象为通用规则。
3. **四要素齐备**：每检查项明确【模块/自动化/评分/闭环】。
4. **优先改规则而非堆例外**。
5. **权重与否决并存**：综合分加权；Fatal 否决不算分。
6. **分层否决**：Fatal A 立即打回；Fatal B 可评分禁发布。
7. **权重可配置**：经 `profiles/` 按类型切换，不写死。
8. **文档不膨胀**：检查项/权重外置，主文档只留原则/支柱/流程。
9. **（v4 新增）三视角独立**：专业编辑/AI工程/读者三方各自独立评分，结论互不替代；发布门禁方可综合。质量分高不得抵消读者体验崩坏。
10. **（v4.2 新增）支柱不内塞**：单一支柱检查项过多时拆子目录（如读者审查拆 `checks/reader/`），主文档只留一级定义；新增只改子文件，不动主文档与模块定义。
11. **（v4.3 新增）门禁驱动结束**：每章是否结束由**门禁决定，不由人拍板**。修复后必须重新跑三支柱门禁（Acceptance Gate）全部 PASS 才进入 Approved；任一 gate 失败回到 Fixing，不允许「差不多了」跳过。
12. **（v4.3 新增）根因优先于症状**：反补不只「修这章问题」，须定位根因（Prompt/流程/规则/脚本/模型）并反补到对应层；同类问题禁止重复发生，一次性笔误不沉淀。

## 2. 支柱一 · 专业编辑审查（质量 · Editor Score）

> 回答：**作品有没有写好？** 覆盖结构/逻辑/人物/世界观等 craft。

### 2.1 编辑审查模块（13 项 · Profile 加权 → ES）
| 模块 | 检查项文件 |
|------|-----------|
| ① 故事结构 | `checks/story.md` |
| ② 剧情逻辑 | `checks/logic.md` |
| ③ 人物塑造 | `checks/character.md` |
| ④ 世界观 | `checks/world.md` |
| ⑤ 设定一致性 | `checks/consistency.md`（与支柱2 双属：编辑定性打分 + 工程定量核验 CI） |
| ⑥ 战斗系统 | `checks/battle.md` |
| ⑦ 情感系统 | `checks/emotion.md` |
| ⑧ 文笔表达 | `checks/writing.md`（内分 8.1 语言规范性 / 8.2 阅读流畅性 Sentence Fluency，含 ZRF 黄金标准） |
| ⑨ 章节质量 | `checks/chapter.md` |
| ⑩ 商业性（含伏笔） | `checks/business.md` |
| ⑪ 叙事审查（v4.2 新增） | `checks/narrative.md`（POV/信息释放/节奏转换/场景切换/描写焦点） |
| ⑫ 对白审查（v4.2 新增） | `checks/dialogue.md`（辨识度/AI腔/推动剧情/暴露设定/信息过载/符合身份） |
| ⑬ 冲突审查（v4.2 新增） | `checks/conflict.md`（章内真实冲突，缺失触发 Fatal B） |

**ES（编辑综合分）＝ Σ(模块_i 得分 × Profile权重_i)**，权重见 `profiles/`（已扩为 13 模块，和＝100）。偏科高分不再掩盖结构崩坏。

### 2.2 权重 Profile 机制
- 权重不写死，由 `profiles/*.md` 按类型提供（默认 `default.md` 玄幻基准）。
- 切换：审查启动时声明类型 → 加载对应 Profile → 加权。任一 Profile 权重和＝100%。
- 清单：玄幻 `default` / 都市 `dushi` / 恋爱 `lianai` / 悬疑 `xuanyi` / 轻小说 `qingxiaoshuo` / 科幻 `kehuan`。

## 3. 支柱二 · AI 工程审查（错误 · Engineering）

> 回答：**有没有 AI 特有错误？** 保证无重复/失忆/上下文断裂/一致性破坏。

| 组成 | 检查项文件 | 输出 |
|------|-----------|------|
| AI 专项（重复4类/失忆/遗忘/节奏） | `checks/ai.md` | AI 错误密度；Fatal A（AI05/AI06 失忆/遗忘） |
| 设定一致性机械核验 | `checks/consistency.md` + `checks/metrics.md` | **CI 一致性指数**（七维一致率均值）；Fatal A（死人复活/前后矛盾） |

- **不计入 ES 加权**，作为独立错误面与门禁 gate。

## 4. 支柱三 · 读者审查（体验 · Reader Review）

> 回答：**这章好不好看、愿不愿继续追、愿不愿付费？** 与编辑质量**平级的一级支柱**，独立评分。
> **v4.2 起拆为 `checks/reader/` 子目录**（遵循元规则 #10），本节点只保留一级定义；具体检查项见子文件。

### 4.1 读者审查组成（一级定义）
| 维度 | 子文件 | 内容 |
|------|--------|------|
| 第一阅读体验 | `reader/first.md` | RR01 第一印象 / RR02 阅读流畅 / RR06 疲劳度（反向计） |
| 情绪与曲线 | `reader/emotion.md` | RR03 情绪体验 ＋ **Emotion Curve 情绪曲线**（平→紧张→高潮→释放→悬念，禁全程平） |
| 奖励与钩子 | `reader/reward.md` | RR04 期待值 / RR05 奖励感 / RR07 爽点兑现 / RR08 信息获取 |
| 沉浸感 | `reader/immersion.md` | **Immersion Score 沉浸感**（出戏检测：现代词/AI解释/作者旁白/破第四面墙） |
| 角色模拟 | `reader/persona.md` | 5 角色（老/新/爽文/剧情党/设定党）＋ **按类型加权 Persona Index** |
| 付费意愿 | `reader/payment.md` | **PI（Payment Intent）** 章末收费愿付比例 |

### 4.2 Reader Index（读者指数）
- **公式**：`Reader Index = mean(RR01, RR02, RR03, RR04, RR05, 100−RR06_疲劳度, RR07, RR08, Immersion)`，各维 0–100。
- 例：第一印象95 / 流畅88 / 情绪82 / 期待88 / 奖励91 / 疲劳15(反85) / 爽点80 / 信息84 / 沉浸90 → RI≈87。
- **门禁阈值：RI ≥ 60**（即便 ES 满分，RI<60 仍禁发布——质量 ≠ 好看）。
- 可选增强：Persona-Weighted Reader Index（按 `persona.md` 类型权重对 5 角色加权）作 NH/商业研判参考。

### 4.3 Payment Intent（PI · 付费意愿）
- 章末若收费，读者愿付费比例 0–100%。**PI<阈值（建议60）＝钩子太弱**。商业小说最关键指标之一，独立于质量分。

### 4.4 Fatal B 触发（读者侧 + 冲突侧）
- **读者侧**：期待值缺失（点不下章）/ 情绪体验平（无一种情绪）/ 疲劳度极高 / 情绪曲线全程平直 → 触发 Fatal B。
- **冲突侧**：`conflict.md` CF01 章内无真实冲突（整章聊天灌水）→ 触发 Fatal B（质量致命·可评分·禁发布）。

## 5. 支柱四 · 发布门禁（Gate）

> 综合三支柱 + Fatal A/B，决定能否出 txt。

### Fatal Gate（跨支柱触发）
- **Fatal A（结构性致命·立即打回·不评分）**：主线崩坏/世界观冲突/时间线错误/人设崩坏/AI失忆/前后矛盾(死人复活·设定冲突)/红线/机械降神。由支柱1/2 触发。
- **Fatal B（质量性致命·可评分·禁发布）**：字数不足/读者审查缺失(RR04缺失/RR03平/RR06极高)/ID灌水/重复4类未去重。由支柱1/3/2 触发。

### 门禁判定（全满足才放行）
> 本门禁即 §7.5 统一验收门口径：任何修改（含审查对话修复落盘）必须重跑全部项，状态方进入 Approved（见 §7.2）。
- [ ] Fatal A 零触发
- [ ] Fatal B 零触发
- [ ] **ES（编辑综合分）≥ 80**
- [ ] **CI（一致性指数）≥ 95%**
- [ ] **Reader Index ≥ 阈值（建议 60）**
- [ ] **PI（付费意愿）≥ 阈值（建议 60）**
- [ ] AI 错误密度达标；logic_check 全码无 FAIL
- [ ] 专名回归；索引一致；NH 健康度达发布阈值

## 7. 五阶段闭环与三层元闭环（v4.3 · 流程升级）

> 核心升级：**串行的「写→查→修→结束」改为迭代回归闭环**。真正成熟的工程（软件/芯片/汽车/游戏）不是「测一次」，而是「直到没有问题为止」。本体系据此引入回归审查、章节状态机、门禁驱动循环、修复三分、根因反补、经验反馈层与三层元闭环。

### 7.1 五阶段闭环（Regression Loop）
```
写作 → 审查 → 修复 → 回归审查 → 定稿
```
- **④ 回归审查（Regression Review）是真正新增的阶段**：不是全量重审，而是**只查「本次修复有没有引入新问题」**（修了 OOC → 剧情断没断？改了设定 → 冲突没冲突？补了伏笔 → 别处漏没漏？）。这正是软件工程里的 Regression——很多 AI「修一个、坏两个」。
- 循环：审查发现 Fatal/Serious/门禁失败 → 修复 → 回归审查 → 仍失败 → 继续修复 → … → 全部 PASS → 定稿。

### 7.2 章节状态机（每章一个状态）
```
Draft → Reviewing → Fixing → Regression -> Approved -> Published
```
| 状态 | 含义 | 进入条件 | 离开条件 |
|------|------|----------|----------|
| Draft | 写作对话已交 md 初稿 | 用户确认 md 初稿 | → Reviewing |
| Reviewing | 审查对话正式审查中 | — | 有 Fatal/Serious/门禁失败 → Fixing；全 PASS → Approved |
| Fixing | 修复中（按 7.4 三分） | 来自 Reviewing/Regression | 修复完 → Regression |
| Regression | 回归审查中（只查引入的新问题） | 来自 Fixing | 有新引入问题 → Fixing；无 → Approved |
| Approved | 门禁全过，待发布 | 来自 Regression | 发布 → Published |
| Published | 已出 txt | — | — |

- **状态必须可机读**：每章在治理索引/大纲登记当前状态；AI 永远知道这章在哪一步。
- **问题计数须单调下降**：第一轮 35 → 修 → 12 → 修 → 3 → 修 → 0 → PASS。任一轮问题数不降（或上升）即判定「修复引入回归」，强制回 Fixing，不允许进入下一阶段。

### 7.3 Review Loop Engine（门禁驱动，不是人决定结束）
```python
state = Draft
while state != Published:
    state = Reviewing
    r = 审查()                      # 三支柱 + Fatal A/B
    if r.FatalA:  修复(); continue  # 结构致命，立即打回
    if r.FatalB:  修复(); continue  # 质量致命，可评分但禁发布
    if r.ReaderIndex < 60: 修复(); continue
    if r.PI < 60:           修复(); continue
    if r.ES < 80:           修复(); continue
    if r.CI < 0.95:         修复(); continue
    # 全部门禁 PASS
    state = Approved
    break
# 发布 → Published
```
- **结束由门禁决定，不由人拍板**：只要任一 gate 失败，自动回到 Fixing，不允许「我觉得差不多了」跳过。

### 7.4 修复三分（避免互相污染）
修复按三类**顺序执行**，不混改：
1. **Engineering Fix（工程修复）**：先修一致性/重复/失忆/索引漂移（支柱2）——基础事实先对齐。
2. **Editorial Fix（编辑修复）**：再修结构/人物/叙事/对白/冲突（支柱1）——在正确事实上调质量。
3. **Reader Fix（读者修复）**：最后修节奏/情绪/沉浸/钩子/疲劳（支柱3）——在质量之上调体验。
> 顺序原因：先改读者体验再改设定容易互相打架；先工程、后编辑、再读者，每层建立在已稳定的下层之上。

### 7.5 Acceptance Gate（验收门 · 统一规则）
> **任何一次修改，都不能自己宣布修好了，必须重新经过三支柱门禁验证才能进入 Approved。**
- 修复落盘后，**必须重跑**：支柱2（logic_check + CI）＋ 支柱1（ES）＋ 支柱3（Reader Index / PI）全量门禁。
- 这正是 `流程体系_小说创作.md` §3「修复后独立复核 / 反模板复验」的升级：从「审查阶段的几个专项闸门」提升为**整个创作流程的统一规则**——修改不直接进定稿。
- 门禁口径见 §5；状态机 7.2 中 Approved 的**唯一**进入条件 = 回归审查后门禁全过。

### 7.6 L6 反馈分层（Feedback → Knowledge Update → System Update）

> **本轮新增**：原反馈层把「知识变更」与「系统变更」混在一起。现明确拆为两条轨道，互不污染：

| 轨道 | 内容 | 落点 | 示例 |
|------|------|------|------|
| **Knowledge Update（知识更新）** | 世界事实变了 | NKB（写 Event / 改对象 Version，见 `NKB.md` §2.1/§2.2） | 「王虎死了」→ 新增 EVT-130 ＋ K2 存活=否 |
| **System Update（系统更新）** | 规则 / Prompt / 流程 / 脚本要改 | `checks/` / 规范 / 流程 / `logic_check` / Prompt | 「Prompt 诱导重复」→ 加 C22 ＋ 改写作对话提示 |

- 反补链 `Problem → Root Cause` 先判定**属于哪条轨道**：事实类 → Knowledge Update；方法类 → System Update。
- 两轨道并行反补、互不阻塞；Knowledge Update 走 NKB 事件驱动，System Update 走下方根因链与经验层。

### 7.6.1 Root Cause 反补（System Update 路径 · 根因优先于症状）
> 反补不只「修这章」，而是**定位根因**后反补到对应层（系统侧），使同类问题不再发生。
```
Problem → Root Cause → Rule → Workflow → Prompt → Script   （System Update 路径）
```
| 层 | 问的问题 | 反补落点 |
|----|----------|----------|
| Root Cause | 为什么会发生？（Prompt？流程？规则？脚本？模型？） | — |
| Rule | 规则缺/歧义？ | `checks/` 检查项 / 元规则 |
| Workflow | 流程漏了一步？ | `流程体系_小说创作.md` / `AI写作自动化流程.md` |
| Prompt | 提示词诱导了错误？ | `novel-chapter-write/SKILL.md` / 写作对话提示 |
| Script | 机检没拦住？ | `logic_check.py` 扩码 / `tools/` |

例（System Update）：发现 AI 重复 → 不只修这章 → 追问根因（生成伪影 / 缺跨章同构约束）→ 反补：C22 扩码 ＋ 写作对话阶段三跨章同构自查（见 `流程体系_小说创作.md` §2 #8）。
例（Knowledge Update）：修复落盘改了「王虎生死」→ 不只改正文 → 写 `EVT-130 王虎身亡` ＋ 同步 `K2 王虎.存活=否`（`Version+1 / Updated Ch130`），供后续章 Context Engine 重放（见 `NKB.md` §2.2）。

### 7.7 经验反馈层（+ Memory）
> 反补链再加一层 **Memory**：每一次项目，系统都变聪明。
```
Problem → Root Cause → Rule → Workflow → Prompt → Script → Memory
```
- Memory = 把已验证的根因＋反补沉淀为**可跨章/跨项目复用**的经验（如「修 OOC 必查剧情链断点」「补设定必查冲突」这类因果对），下次同因直接调用，不再从零排查。
- 落点：共性问题入 `写作规则.md` / `流程体系_小说创作.md` §2 映射表；根因经验入 `tools/` 或本体系经验库；一次性笔误不沉淀。

### 7.8 三层闭环（双闭环 + 元闭环）
```
① 章节闭环（第一层）：写作 → 审查 → 修复 → 回归审查 → 定稿
        ↓ 问题汇总
② 项目闭环（第二层）：所有章节问题 → 趋势/共性分析 → 更新规则/脚本/检查项（补「类」）
        ↓ 流程效果评估
③ 体系闭环（第三层 · 元闭环）：流程运行效果 → 评估流程本身 → 优化工作流/门禁/自动化/Prompt
```
- **第一层**保证这一章最终质量（7.1–7.5）。
- **第二层**保证同类问题不在后续章节重复（与现有「问题→流程改进」一致，但范围扩到整个项目趋势）。
- **第三层（元闭环）是本次补上的唯一缺口**：不只演进小说内容，还**演进流程本身**——定期评估门禁阈值是否合理、脚本是否漏检、Prompt 是否诱导错误、元规则是否需要增改；评估结论直接改 `审查体系.md`（L1/L2）/ `流程体系_小说创作.md` / `logic_check.py` / Prompt。由此从「一套小说创作流程」升级为「能持续自我优化的 AI 创作系统」。

## 7.9 Delta Review（增量审查 · 局部快审）

> **本轮新增**：回归审查（§7.1④）只查「修复引入的新问题」，但仍可能跑全量三支柱。当改动仅限**局部块**（一句 / 一段 / 单个人物设定），没必要重跑全部——否则闭环太慢。Delta Review 是**局部修改快审，全量只按需触发**的加速机制。

**触发与流程**：
```
Modified Block（被改最小单元：句/段/场景/单对象）
   → Scope 分析（影响了哪类事实 → 映射受影响的 checks / CI 维度 / 读者维度）
   → 只跑受影响子集（Delta Review）
   → PASS 且 scope 小 → 标记 Approved（免全量，仍须走 §7.5 受影响项）
   → FAIL 或 scope 大 → 触发 Full Review（§7.1 全量三支柱）
```

**范围映射（示例）**：
| 改动类型 | 触发 Delta 检查项 | 是否需 Full |
|----------|-------------------|-------------|
| 改一句对白 | `checks/dialogue` + C22 重复 + 读者 C3 | 否（除非波及冲突） |
| 改单个人物设定 | `checks/character` + CI 人物维 + OOC | 否 |
| 改世界态/事件 | `checks/world` + CI 设定维 + K4 派生核对 | 视波及范围 |
| 改章末钩子 | `checks/reader/reward` + B2 + PI | 否 |
| 改主线 / 大段重写 | — | **是（必全量）** |

**规则**：
- Delta PASS 且 scope 小 → 不强制 Full，但**仍须走统一验收门口径（§7.5）的受影响项**；Approved 条件不变。
- Delta FAIL 或无法判定 scope → 立即升 Full Review，不得「局部过了就放行」。
- Delta 结果记入 Fix Log（见 Workflow Build 产物，§流程体系 §3.1），供回归追踪。
- 提速本质：**局部修改快审，全量只按需触发**——闭环效率显著提升，与用户要求的「增量执行」一致。

## 7.10 静态 / 动态评测分轨（Static → Dynamic → Gate）

> **本轮新增**：四支柱内部其实有两类本质不同的检查——**静态**（几乎不需 LLM，规则/脚本可判）与**动态**（需读者模拟 / 语义理解）。混跑拖慢闭环。故分轨：**静态先行（快、便宜），动态后行（重、需模拟），最后汇入门禁**。

**静态评测（Static · 近乎零 LLM）**：
| 检查 | 来源 | 判定方式 |
|------|------|----------|
| 重复 4 类 | `checks/ai.md` ＋ C22 | 脚本正则 |
| 逻辑 / 一致性 | `checks/consistency.md` ＋ CI | 机械比对 NKB |
| 现代词 / 破墙 | R19 ＋ `checks/metrics.md` | 锁词表 grep |
| 索引漂移 | FB/伏笔/角色索引 | 交叉比对 |
| 字数 / 专名回归 | logic_check | 脚本 |

**动态评测（Dynamic · 需读者模拟 / 语义）**：
| 检查 | 来源 | 判定方式 |
|------|------|----------|
| 读者指数 / 沉浸 / 情绪曲线 | `checks/reader/` | 5 Persona 模拟 |
| 情感 / 奖励 / 钩子 | `checks/emotion.md` ＋ reader | 语义理解 |
| 冲突质量 / 对白辨识度 | `checks/conflict.md` ＋ dialogue | 语义评判 |
| Fatal B 读者侧 | §4.4 | 体验判定 |

**分轨流程**：
```
静态评测（脚本/正则，秒级、近乎零 LLM）
   → 全 PASS → 仅跑必要动态子集（避免每章全量读者模拟）
   → 动态评测（读者模拟，重）
   → 汇入门禁（Fatal A/B ＋ ES ＋ CI ＋ RI ＋ PI）
```
- **提速本质**：静态问题（重复/现代词/索引）先拦，动态评测只针对「过静态」的稿——与 §7.9 Delta Review 叠加，局部修改几乎只跑静态 ＋ 受影响动态子集，闭环大幅提速。

## 8. 执行 SOP（五阶段闭环落地）

> 本 SOP 即 §7 五阶段闭环的逐章落地：每章从 Reviewing 起，按门禁驱动循环跑完 审查→修复→回归→Approved；状态机见 §7.2，验收门见 §7.5。

**输入**：审查要求 ＋ 范围 ＋ 类型(决定 Profile) ＋ 磁盘索引/大纲（含该章当前状态）。

**步骤**：
1. **解析范围与 Profile**：确认章号/批次/跨卷；加载 `profiles/*.md` 权重。
2. **支柱2 前置（Fatal A）**：先扫结构致命（主线/世界观/时间线/人设/AI失忆/前后矛盾/红线/机械降神）。**命中→直接打回**。
3. **（静态评测先行·近乎零 LLM）支柱2 工程核验**：logic_check 全码 ＋ 跨章同构 ＋ 重复4类 ＋ 专名回归 ＋ 量化扫描 ＋ ID/WBU 统计 → 算 CI。（静态/动态分轨见 §7.10）
4. **支柱1 编辑深读**：对 ①–⑬ 逐检查项（`checks/*.md`）判 PASS/FAIL ＋ 证据 → 按 Profile 算 ES（含 v4.2 新增 ⑪叙事/⑫对白/⑬冲突）。
5. **支柱3 读者审查**：按 `checks/reader/` 子文件评各维 → 算 Reader Index（含 Immersion）；评 Emotion Curve；评 PI；做 5 角色模拟（按类型加权）。
6. **Risk**：产出概率列表；算 NH（ES+CI+RI+AI+Risk）。
7. **版本比对**：比对上轮 vN-1 分数演变。
8. **Fatal B 判定**：命中→门禁禁发布（仍输出完整三支柱评分）。
9. **处置**（须走 §7.5 统一验收门）：硬伤直接落盘；创作取向给写作对话；**修复落盘后必须重跑三支柱门禁（logic_check＋CI＋ES＋Reader Index/PI）全部 PASS** 方可标记 Approved（对应状态机 §7.2）；并做「修复后独立复核 ＋ 字数复验」（防假通过）。**局部修改优先走 §7.9 Delta Review 快审；仅当 Delta FAIL 或 scope 大才升全量。**
10. **输出**：`审读_NNN-NNN_vN评分卡.md`（四支柱报告）。

## 9. 验收标准（DoD · 可出 txt）

一章可出 txt 当且仅当：Fatal A/B 双零 ＋ ES≥80 ＋ CI≥95% ＋ Reader Index≥60 ＋ PI≥60 ＋ logic_check 无 FAIL ＋ 专名回归 ＋ 索引一致 ＋ ID 不预警 ＋ WBU≥阈值 ＋ NH 达发布阈值 ＋ 字数≥2500 ＋ 反模板复验通过 ＋ ⑬冲突审查 CF01 非缺失（章内有真实冲突）。
