# AI 上下文引擎（Context Engine）

> **定位**：编排器调用的**支撑引擎**（非独立流程层）。把 NKB 事实 + 规划卡 + 读者态 + 记忆 加工为**运行时上下文（Runtime Context）**，供 Workflow 统一读取。
>
> **本次升级（v2）**：原 Context Builder 只做「拼接标准背景块」，面对长篇（几百人物 / 几百伏笔 / 几十页世界态）会**上下文爆炸**——AI 根本放不下。故升级为**引擎**：在「组装」之外新增四道运行时能力——**过滤 → 优先级 → 压缩 → 冲突解决**，输出**可预算、可裁剪、无冲突**的最终上下文。
>
> 它仍是「只拼背景」，但现在是**带运行能力的拼装**，而非朴素拼接。

---

## 1. 输入（Inputs）

从 NKB 与规划层抽取本章**候选**事实（尚未过滤）：

- **NKB**：人物 / 世界 / 时间线 / 伏笔 / 术语（见 `NKB.md`，含 Version 与事件驱动态）
- **本章规划卡**：L3 规划者产出（目标 / 节拍 / Story Beat / 冲突 / 情绪曲线 / 预算）
- **上一章结尾**：衔接点
- **伏笔状态**：已埋 / 进行中 / 已收（含临近 deadline）
- **时间线锚点**：本章年份 / 章节位置
- **读者态（Reader State）**：进度 / Persona 疲劳度 / 期待点（见 `checks/reader/persona.md`）
- **记忆（Memory）**：跨项目因果对 / 长期偏好（见 L6 反馈层）

> 输入是「全集候选」，引擎后续四阶段把它裁成「本章真正需要的」。

---

## 2. 四阶段流水线（核心升级）

```
候选事实(NKB+规划+读者态+记忆)
   │
   ▼ ① 上下文过滤器 Filter
   │   （只取本章需要的：时间窗/空间/出场人物/相关伏笔/可见世界态）
   ▼ ② 上下文优先级 Priority
   │   （给过滤后事实打分；决定「哪些不能丢」）
   ▼ ③ 上下文压缩 Compression
   │   （100KB → 20KB：摘要/去重/折叠/引用）
   ▼ ④ 冲突解决 Conflict Resolve
   │   （NKB vs 最新修复/草稿 冲突，谁优先？）
   ▼
Final Context（标准背景块 ＋ 优先级标注 ＋ 压缩痕迹 ＋ 冲突裁决）
```

### 2.1 上下文过滤器（Context Filter）

**目的**：长篇小说里，第 500 章没必要读取第 5 章的所有人物。过滤器按「本章相关度」**只取真正需要的**。

过滤维度（任一不满足则剔除）：

| 维度 | 规则 | 示例 |
|------|------|------|
| 时间窗 | 本章 ±N 章 / 当前卷内相关；远章仅保留「持续生效事实」 | 第 500 章不载入第 5 章路人甲全档案 |
| 空间 | 本章场景所在势力 / 地点内的世界态与人物 | 江南场景不载入漠北专属伏笔细节 |
| 出场人物 | 本章 POV + 出场名单 + 其直接关系人（1 跳） | 王虎（挚友）→ 载入；王虎远亲不载入 |
| 相关伏笔 | 本章需推进 / 临近 deadline / 与出场人物相关 | FB-007 死线临近 → 载入；百年后回收的伏笔 → 不载入 |
| 可见世界态 | 本章视角「能看到」的世界切面（依 D2 读者态） | 读者不知的幕后黑手 → 不向草稿泄露 |

**输出**：`Filtered Context`（候选事实的子集，仍可能超预算）。

> 过滤器解决「放不下」的第一层：先砍不相关的，再谈压缩。

### 2.2 上下文优先级（Context Priority）

**目的**：压缩后仍可能超预算时，知道**哪些不能丢**。

默认优先级（可经 `profiles/` 覆盖；数值越高越不可丢）：

| 类别 | 默认权重 | 说明 |
|------|----------|------|
| 人物（出场+关系） | 100 | 本章直接驱动情节，最高优先级 |
| 冲突（本章核心） | 90 | 对抗双方 / 升级点，缺则章塌 |
| 伏笔（相关+死线） | 80 | 回收节奏敏感，漏则读者遗忘 |
| 世界背景 | 50 | 氛围与设定，可摘要 |
| 设定术语 | 40 | 专名一致性，可引用不内联 |
| 时间线 | 30 | 锚点即可，详链可查 |

**裁决规则**：当 `Filtered Context` 超出预算（见 §3 压缩预算），**从最低优先级起裁**，直至达标；被裁项以「引用句柄」保留（如 `参见 NKB/K2/CHR-001`），Workflow 按需查。

### 2.3 上下文压缩（Context Compression）

**目的**：把 `100KB` 压到 `20KB`，避免 Claude / GPT 上下文爆炸。

压缩策略（保高优先级事实，降体积）：

1. **摘要化**：长设定 → 一句话（「武者登记制：朝廷 census 所有武者，违者重罪」）。
2. **去重**：合并多章重复的同一事实描述，只留权威一句。
3. **折叠历史**：详细事件 → 三元组 `(谁, 何事, 影响)`（见 NKB 事件驱动态）。
4. **引用而非内联**：NKB 对象以 `ID` 引用（如 `CHR-001`），详情按需查 NKB，不整段铺进 Context。
5. **结构化替散文**：表格 / 键值对替代大段说明。

**压缩预算**：由 §2.5 Context Budget 推导（默认总预算 32000 Token；长章 / 大场面可临时上调）。引擎记录「压缩痕迹」（哪些被摘要 / 引用），便于回归审查核对「是否压丢了关键事实」。

### 2.4 冲突解决（Conflict Resolution）

**目的**：NKB 与「最新修复 / 草稿」冲突时，**谁优先**有明确定义——目前系统缺此定义。

**Resolution Policy（裁决策略）**：

1. **NKB 是 SSOT（最高优先）**：任何与 NKB 冲突的草稿事实，以 NKB 为准（除非该草稿是**尚未回写 NKB 的新事件**）。
2. **修复须同步 NKB（M3）**：落盘修复若改了事实（如王虎生死），**必须同步更新 NKB 对应组件**；未同步则 NKB 仍优先，并标记 `待同步`。
3. **新事件回写**：草稿引入的新事实（如第 132 章商城开业）→ 作为 Event 回写 NKB（事件驱动态），经事件派生世界态，不手动改 State。
4. **产出 Conflict Report**：列出每条冲突（冲突方 / 裁决 / 动作 / 是否需回写 NKB）。

> 冲突解决让「修一个、坏两个」的回归风险在 Context 层就被拦截——Workflow 拿到的永远是**裁决后的一致上下文**。

### 2.5 上下文预算（Context Budget）

**目的**：压缩「压多少」不能拍脑袋——必须有**量化预算**。过滤器/优先级解决「留什么」，预算解决「给每类留多少空间」。

**默认 Token Budget（可配置，与 §2.2 优先级同构）**：
| 预算块 | 总配额（Token） | 对应优先级 | 说明 |
|--------|----------------|-----------|------|
| 总预算 | 32000 | — | 单章 Final Context 硬上限 |
| 人物 | 8000 | 100 | 出场＋关系，最高配额 |
| 冲突 | 6000 | 90 | 对抗双方 / 升级点 |
| 伏笔 | 4000 | 80 | 相关＋死线 |
| 世界背景 | 6000 | 50 | 氛围 / 设定，可摘要 |
| 设定术语 | 3000 | 40 | 专名一致性，可引用 |
| 时间线 | 2000 | 30 | 锚点即可 |
| 余量 | 3000 | — | 缓冲（冲突裁决 / 压缩痕迹 / 红线） |

**预算驱动压缩**：§2.3 压缩目标 = `总预算 − 已用`。当 Filtered Context 估算超总预算，**先按优先级裁低优先级块**（术语/时间线先砍），再对保留块做摘要/引用压缩至配额内；被裁块以引用句柄保留，不丢事实。
**预算超支告警**：即便裁到最低优先级仍超（如大场面需更多信息）→ 引擎标 `预算超支` 并建议临时上调总预算或拆章，不静默膨胀。

## 3. 输出（Output）

**Final Context（标准背景块 · 运行时版）**：

```
【本章背景 Runtime】
- 目标：___
- 冲突（优先级90）：___（对抗双方 / 升级点）
- 情绪曲线预期：平→紧张→高潮→释放→悬念
- 预算：开头___ 铺垫___ 冲突___ 高潮___ 结尾___
- 人物事实（优先级100，已过滤+引用）：___（来自NKB/K2，ID 引用）
- 世界事实（优先级50，已压缩）：___
- 时间线：___
- 伏笔（优先级80，相关+死线）：已埋___ 进行中___ 本章需推进___
- 上章衔接：___
- 读者态：___
- 红线/宪法边界：___
- 预算占用：总 32000 / 已用 XXXX / 超支否（见 §2.5）
- [引擎元信息] 过滤剔除N项 / 压缩 100KB→XXKB / 冲突裁决M条 / 待同步K项
```

> Workflow（L4）每次写前**统一读取此块**；禁止在 Prompt 里临时拼人物 / 设定 / 时间线。

---

## 4. 规则

1. **唯一入口**：Final Context 是写前上下文的唯一来源；任何「临时在 Prompt 加人物设定」视为违规。
2. **由编排器调用**：编排器在 Loop 每轮开始时运行引擎（反映最新 NKB / 伏笔 / 修复结果）。
3. **预算硬约束**：Final Context 超出压缩预算时，按优先级裁并保留引用句柄，不得无限膨胀。
4. **审查可复用**：L5 Review 也可用同一 Final Context 核对成稿是否偏离事实（与 NKB 基准一致）；压缩痕迹供回归审查核对「是否压丢关键事实」。
5. **冲突裁决留痕**：所有冲突裁决入 Conflict Report，供 L6 反馈层评估「知识更新」需求。

---

## 5. 与架构的关系

```
NKB（SSOT）──┐
规划卡    ───┤
上章/伏笔 ───┼─▶ Context Engine ─(过滤/优先级/压缩/冲突解决)─▶ Final Context ─▶ L4 Workflow
读者态    ───┤                                                              ↑ 统一读取
记忆      ───┘
         （由 Orchestrator 经 Plugin 调度）
```

> 引擎是「运行能力」而非「规则」：它不定义小说该怎么写，只保证**上下文在任意篇幅下都放得下、裁得准、压得动、无冲突**。
