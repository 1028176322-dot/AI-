# 自主学习与反馈闭环

平台的“学习”不是让模型直接改写全局规则，而是把证据转成可追踪候选，并在任务、审批、项目验证和回归测试之后逐级启用。

## 1. 参考小说学习

1. 用户授权的 TXT/MD 原著只放入新项目 `sources/references/inbox/`，默认不进入 Git。
2. `platform learn analyze|batch` 只提取结构统计、节奏信号和抽象原则，不复制原文段落。
3. 产物进入 `learning/candidates/`，同时生成面向写作和审查的候选。
4. `promote-project --approved` 仅可把候选作为当前项目实验规则写入 `memory/project/reference-learning/` 与 `runtime/learning/reference-guidance.yaml`。
5. 参考书数量不是独立项目验证数。类型级、全局级晋升仍须遵守 `memory/晋升机制.md`，不能因多本参考书自动升级。

## 对话请求必须先拆成任务

用户可以直接在 AI 对话框输入“写十章”“写第 21—30 章并审查”或“审查最新五章”。AI 必须先调用 `platform task dispatch --request`。脚本会确定性解释数量或范围，记录默认假设，并在实际项目的 `tasks/goals/`、`tasks/<state>/` 和 `runtime/task-packets/` 中建立完整执行记录。对话内容本身不是写入授权。

## 2. 审查反补写作

`task review` 的 findings 由 `feedback_learning.py` 自动聚合。每条问题被转换为：

- 可在下次写作前执行的写作约束；
- 可在下次审查中复测的回归检查；
- 带任务、章节、频次和严重度的项目私有证据。

一次问题只记录为 observed；跨章节复现后才成为 promotion candidate。上下文构建器自动把项目级写作约束、参考实验规则和回归检查注入对应写作、修复、审查任务。

## 3. 读者证据

新项目的内容审查必须完成十二镜头 Reader Panel。面板由同一个 Agent 串行切换观察点，不创建子 Agent；每个镜头都必须填写正文位置、阅读影响、预期和修复建议。

AI 面板属于预测证据，绝不冒充真实读者。真实读者反馈通过 `reader-panel ingest-human` 单独摄取，至少三名参与者，并记录样本分群、读完率、推荐意愿、付费意愿和停读点，用于校准 AI 预测。新项目在试读、卷末、付费边界和重大修订里程碑必须建立 `human_gate` 任务。

## 4. 治理边界

- 无 Task、无 Claim、无当前 Session，不得写入。
- 平台变更必须有 `system_maintenance` 任务记录。
- 带 `PROJECT_LAYOUT.yaml` 的新项目对所有内容、配置、学习、分析和生成文件启用严格写入治理。
- 现有项目没有目录标记时保持旧版兼容，不自动迁移。
- 正式章节只能由 Publish Service 写入；学习流程不能直接写 NKB、正式章节或平台全局记忆。

## 5. 可复用脚本边界

脚本负责确定性工作：文本统计、哈希、目录生成、候选聚合、问题签名、回归清单、契约校验、任务状态和证据落盘。需要语义判断的“为何有效、是否适配、如何修复”由单 Agent 在证据模板中完成。这样既减少重复劳动，也避免把启发式统计误当文学结论。
