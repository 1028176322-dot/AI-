# 章节全链路自动推进规范

> 状态：strict-v2 现行执行规范
> 生效日期：2026-07-29
> 实现：`scripts/chapter_pipeline_driver.py`
> CLI：`platform chapter-flow run/status`

## 1. 目标

把“每章由 AI 手工认领、启动、写产物、发事件、寻找下一任务”的流程收口为一个
可续跑入口。平台脚本负责状态识别、确定性产物、合同校验和事件路由；当前主 AI
只处理真正需要语义判断的工作。

这项优化不降低门禁，不把文学判断伪装成正则结果，也不允许跳过 Task、Session、
Broker、NKB、读者审查、人工授权或 Publish Service。

## 2. 唯一入口

```powershell
platform chapter-flow run --project-root "<PROJECT_ROOT>" --chapter "CH-NNN" --agent "<AI_ID>"
platform chapter-flow status --project-root "<PROJECT_ROOT>" --chapter "CH-NNN"
```

正常执行禁止直接运行 `scripts/chapter_pipeline_driver.py`，禁止让不同 AI 各自拼装
`task_cli.py`、`style_cli.py`、`chapter_cli.py` 或底层 Python 调用链。

## 3. 自动与语义边界

| 类别 | 环节 | 行为 |
|---|---|---|
| 自动 | 找到当前章节真实 task frontier | 扫描 task 状态，不相信对话记忆 |
| 自动 | Author Executor 接入 | 有批准适配器则执行；否则只生成交互交换文件 |
| 一次语义包 | chapter review + AI Reader Panel | 同一次深读完成两份绑定报告 |
| 自动 | protected manifest | 构建、校验、持久化、发事件 |
| 自动 | AI diagnosis | 优先复用已通过 chapter review 的语义 clearance，避免重复 LLM 审查 |
| 自动 | final regression | 绑定正文、NKB、章纲、manifest、guidance、review hash |
| 一次语义包 | NKB candidate disposition | knowledge-manager 逐项接受、拒绝或标冲突 |
| 自动 | NKB sync | canonical 校验、同步证明、事件路由 |
| 自动 | post-NKB rebind | 重建 manifest、复用 clearance、重跑 final regression |
| 自动 | publish | 仅调用 Publish Service/Broker |
| 语义/人工 | fix、style revise、human gate、outline refresh | 暂停并给出精确工作单 |

## 4. 为什么 NKB 同步后还要自动重跑尾链

第一次 final regression 证明“这份正文与写作时使用的 NKB 一致”。本章事实回补后，
NKB 的 revision/hash 可能改变。若直接发布，`nkb_sync_proof` 与旧 regression
必然不一致，或者只能伪造旧 hash。

因此强制链是：

```text
final-regression(initial)
→ nkb_update
→ nkb_sync
→ protected-manifest-build(post_nkb_sync)
→ ai-diagnose(reuse review clearance)
→ final-regression(on_pass_post_nkb)
→ chapter_publish
```

第二段全部是确定性自动重绑定，不增加一次文学审查，也不会再次创建 `nkb_update`。

## 5. 断点、幂等与恢复

驱动器每次都从真实 task 文件重建前沿，并写：

```text
runtime/chapter-pipeline/CH-NNN/state.json
runtime/chapter-pipeline/CH-NNN/NEXT_ACTION.json
```

- 已完成事件由任务系统幂等保护，不重复创建后继。
- 已通过 Author 响应合同的同一请求可复用缓存，不重复调用模型。
- 交互式 Author 未显式传 `--agent` 时继承 claimed/running 任务 owner，避免
  默认身份与任务租约冲突；显式传错 owner 仍拒绝。
- 章纲先从 Task Packet 的 `chapter_plan` 绑定解析，再回退
  `PLAN-NNN.yaml`，不依赖任务 ID 的命名形态。
- 有效发布任务在目标完全一致时可续期系统 task grant；默认窗口 24 小时。
  该续期不触碰真人 human gate 授权。
- `PAUSED` 表示等待合法语义产物，不是失败。
- 按工作单指定的平台任务执行器完成语义 Task 的提交/事件后，重复同一条
  `chapter-flow run` 即可续跑；不得自行组合未声明的 stage。
- `BLOCK` 必须修复具体错误；不得删除任务、手改状态或改走旁路。

## 6. 性能验收口径

性能不再按“执行了多少条手工命令”衡量，而按以下指标验收：

1. 干净路径没有逐 stage 人工 claim/start/event。
2. 同一份已通过 chapter review 可为 diagnosis 提供 clearance，不重复做同义审查。
3. YAML、reader evidence、manifest revision、approved_event、task facade 均有回归测试。
4. NKB 更新后的 hash 漂移由自动重绑定解决，不在 publish 阶段才暴露。
5. 确定性阶段只受本机 I/O、验证器和 Broker 延迟影响；不得触发额外 LLM 调用。
6. 总耗时主要由正文创作、一次深度审查、NKB 取舍及必要的人类/大纲决策构成。

## 7. 禁止事项

- 把 `PAUSED` 当成失败，然后直接改 `chapters/drafts/` 或 `approved/`。
- 为提速跳过 Reader Panel、NKB sync、post-NKB regression 或 outline refresh。
- 手写 `approved_event`、同步证明、回归结果或人工授权。
- 在对话记忆里维护 stage 进度而不读 task 状态。
- 多个 AI 同时推进同一章节 task。
- 复制驱动脚本到项目目录形成项目私有版本。
- 把系统 publish grant 续期解释为真人授权，或用续期改变 publish_target。
